# Резервна копія даних

Найважливіше в цьому документі — перший абзац.

## Supabase не робить копій вашої бази

На безкоштовному тарифі — **жодних**. Не «сім днів», не «обмежено».
Їхня власна документація радить безкоштовним проєктам експортувати
дані самостійно.

Автоматичні щоденні копії починаються з Pro (7 днів), Team — 14,
Enterprise — до 30. Відновлення на точку в часі (PITR) на безкоштовному
тарифі теж недоступне.

А в базі лежить усе, чого немає більше ніде:

| Що | Чим це є насправді |
|---|---|
| `orders`, `order_refusals` | вся історія замовлень і відмов |
| `reviews`, `review_requests` | відгуки покупців |
| `profiles`, `addresses` | імена, телефони, адреси доставки |
| `cart_items`, `favorites` | кошики й обране |
| `promo_codes` | хеші промокодів |
| `site_issues` | журнал подій сайту |

Сайт, товари, ціни й сторінки відновляться з git за хвилину.
**Замовлення не відновляться нізвідки.**

## Що зроблено

Workflow **Backup data** щонеділі о 03:00 UTC:

1. вивантажує ці таблиці в JSON (`scripts/backup-data.js`);
2. пакує в `tar.gz`;
3. **шифрує** паролем із секретів (`gpg`, AES256);
4. кладе як артефакт Actions на 90 днів.

Тобто під рукою завжди близько тринадцяти щотижневих копій.

### Чому шифрування обов'язкове, а не бажане

Репозиторій **публічний**. GitHub пише, що для завантаження артефакта
потрібен «доступ на читання» — а в публічного репозиторію такий доступ
має будь-хто. Покладатись на це не можна: в архіві імена, телефони й
адреси покупців.

Тому крок **не вивантажує нічого**, поки пароля немає. Це не помилка
налаштування, а відмова робити небезпечну річ: відкрита копія
персональних даних гірша за відсутність копії.

### Чого копія НЕ покриває

**Акаунтів покупців.** Пошта й пароль лежать у схемі `auth`, а
PostgREST віддає лише `public` — дістати їх цим шляхом неможливо.

Практично це означає: якщо проєкт зникне, замовлення й відгуки
повернуться, а людям доведеться зареєструватись заново. Профілі
(`profiles`) у копії є, тож ім'я й телефон замовника не втратяться.

Ще не копіюємо навмисно:

- `stock`, `prices` — це знімки з репозиторію, перезбираються
  командою `npm run build`;
- лічильники звернень і `throttle_salt` — нічого не означають поза
  своєю годиною;
- `bot_sessions` — недописані чернетки замовлень у боті.

## Що зробити один раз

**Settings → Secrets and variables → Actions → New repository secret:**

| Name | Value |
|---|---|
| `BACKUP_PASSPHRASE` | довгий пароль, який ви **не втратите** |

⚠️ Цей пароль — єдиний спосіб відкрити архів. Немає «відновлення
пароля»: втратите його — копії стануть непотрібними файлами. Покладіть
його туди ж, де тримаєте інші важливі паролі.

Далі **Actions → Sync branches → dev-to-main**: GitHub бере розклад
тільки з головної гілки.

## Як перевірити

**Actions → Backup data → Run workflow.** У логу буде видно, скільки
рядків узято з кожної таблиці. Артефакт з'явиться внизу сторінки
запуску.

Локально, без секретів, — просто порахувати рядки:

```bash
node scripts/backup-data.js --dry-run
```

(потрібен `SUPABASE_SERVICE_ROLE_KEY` у змінних середовища)

## Як відкрити копію

```bash
gpg --decrypt backup.tar.gz.gpg > backup.tar.gz
tar -xzf backup.tar.gz
```

Усередині — по одному JSON на таблицю й `README.txt` з датою, адресою
проєкту та порядком відновлення.

## Як відновити

Порядок важливий: спершу `profiles` і `addresses`, потім `orders`, і
вже потім те, що на них посилається. Він же виписаний у `README.txt`
всередині архіву.

Найпростіше — **Supabase → Table Editor → Import data**, або через
PostgREST службовим ключем.
