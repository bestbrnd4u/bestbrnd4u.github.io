# Моніторинг

Хто перший дізнається, що магазин зламався.

## Коротко

| Що перевіряється | Як часто | Що буде, якщо зламалось |
|---|---|---|
| Сайт відкривається, каталог не порожній | кожні 30 хв | лист від GitHub про провалений запуск |
| Помилки в браузерах покупців | раз на добу | лист від GitHub зі списком |

Обидві перевірки живуть в Actions → **Monitor**.

---

## Чому лист приходить від GitHub

Окремого сервісу моніторингу тут немає — і не потрібно. GitHub сам
пише власнику репозиторію про кожен провалений workflow. Тому
перевірка не «доповідає про проблему», а **падає**: це найкоротший
шлях від «зламалось» до листа, без стороннього сервісу й без ще
одного секрета.

Лист приходить на пошту акаунта. Якщо не приходить — GitHub → Settings
→ Notifications → **Actions** → увімкнути «Send notifications for
failed workflows only».

---

## Що саме перевіряється ззовні

`scripts/monitor.js` відкриває прод так само, як це зробив би
покупець, і дивиться не лише на «чи відповідає»:

- головна й каталог віддають 200 і містять розмітку магазину;
- `data/products.json` розбирається і містить **не менше половини**
  тих товарів, що лежать у репозиторії (порожній каталог після
  зламаної збірки виглядає як цілком робочий сайт);
- у всіх товарів є ціна;
- перша сторінка товару з sitemap відкривається й **несе назву та
  ціну** в розмітці schema.org — кнопку «Купити» малює JavaScript, тож
  її наявність у відповіді нічого не доводила б;
- усі адреси в sitemap ведуть на цей самий домен, а не на дев;
- `robots.txt` не забороняє індексацію, а сторінки не позначені
  noindex;
- фід має позиції;
- неіснуюча адреса віддає **404** і показує сторінку магазину;
- **розгорнута функція знає про маршрут** `checkout-draft` — тобто її
  перерозгорнули після міграції 020.

Останній пункт — про окремий вид тихої поломки. Нова можливість
функції жива лише після ДВОХ дій: міграція в базі й
`supabase functions deploy telegram-order-bot`. Пропустити друге
легко: код у гілці є, тести зелені, а на сайті мовчок. Перевірка
питає функцію навмисно недійсними даними — у базу нічого не
пишеться, — і за самою відмовою бачить, чи маршрут у ній є.

Останні три — найважливіші. Сайт із дев-налаштуваннями на проді
працює бездоганно і при цьому зникає з пошуку: жодна сторінка не
виглядає зламаною, а замовлень стає менше через місяць.

### Запустити руками

```
node scripts/monitor.js                      прод
node scripts/monitor.js --env=development    дев
node scripts/monitor.js --url=https://…      будь-що
```

## Помилки в браузерах покупців

Поламана сторінка нічого не показує: кнопка не спрацювала, каталог не
намалювався — людина закриває вкладку. У консолі власника при цьому
все гаразд, бо в нього інший браузер і свіжий кеш.

Тепер сторінка сама розповідає, що в неї впало
(`assets/js/error-report.js`): адреса, текст помилки, файл і рядок,
назва браузера. Плюс окремо — **адреси, яких немає**: коли хтось
приходить за битим посиланням, у журналі лишається сама адреса й
звідки прийшли. Саме так знаходяться посилання, поставлені колись у
рекламі чи в описі профілю.

Нічого особистого туди не потрапляє: ні імені, ні пошти, ні кошика.
Навіть параметри адреси відрізаються — у них буває пошуковий запит.

### Три обмеження, щоб журнал лишався журналом

Запис у базу — єдине, що сайт дозволяє робити відвідувачу без
замовлення, тож функція `report_issue` захищена трьома правилами:

1. **Дедуплікація.** Та сама помилка на тій самій сторінці — це +1 до
   лічильника, а не новий рядок. Поламаний цикл дає сотні однакових
   повідомлень за секунду.
2. **Обрізання.** Довгі тексти ріжуться в самій базі, а не з довіри до
   браузера.
3. **Стеля.** Якщо за годину з'явилось 200 РІЗНИХ помилок — нові не
   створюються. Стільки різних помилок означає або катастрофу, яку й
   так уже видно, або те, що хтось надсилає випадковий текст.

Сторінка від цього не залежить узагалі: не записалось — значить не
записалось, жодного повідомлення покупець не побачить.

### Де подивитись

Supabase → Table Editor → `site_issues`, або запитом:

```sql
select kind, page, message, hits, last_seen
  from public.site_issues
 order by last_seen desc
 limit 50;
```

Полагодили — рядок можна видалити. Раз на добу крок «Зведення помилок
сайту» бере нові записи, показує їх у листі й ставить `notified =
true`, щоб не повідомляти про те саме двічі. Помилка, яку не
полагодили, далі росте лічильником, але листами більше не докучає.

## Що потрібно ввімкнути один раз

**1. Перенести в main.** GitHub бере розклад тільки з головної гілки.
Actions → **Sync branches** → dev-to-main. Поки цього немає,
моніторинг мовчить.

**2. Міграція.** Supabase → SQL Editor → виконати
`supabase/migrations/013-site-issues.sql`. Без неї журнал помилок
просто нікуди не пише (сайт при цьому працює як завжди).

**3. Секрет.** `SUPABASE_SERVICE_ROLE_KEY` у секретах репозиторію —
той самий, що вже потрібен для списання залишків. Якщо він уже є,
робити нічого не треба. Без нього зведення помилок пропускається, а
перевірка доступності працює як зазвичай.

---

## Чого це не робить

- **Не перевіряє дев.** Тестова копія падає й піднімається за задумом;
  листи про неї були б шумом. Перевірити руками: `--env=development`.
- **Не ловить помилок, які не кидають винятку.** Кнопка, що працює,
  але веде не туди, лишається в межах відповідальності тестів.
- **Не будить уночі.** Це пошта, а не пейджер: між поломкою й листом
  може минути до пів години.

## Заголовки безпеки: що ввімкнути в Cloudflare

Це **не робота в коді**: сайт віддає GitHub Pages, а він не дозволяє
задавати свої заголовки. Файл `_headers` теж не працює — це
можливість Cloudflare Pages, а не проксі перед GitHub.

⚠️ Тут раніше було написано, що два заголовки Cloudflare додає сам
(`x-content-type-options` і `referrer-policy`). **Це неправда** —
заміряно на проді:

```bash
curl -sI https://bestbrnd4u.com/ | grep -iE "strict-transport|content-security|x-frame|x-content-type|referrer-policy|permissions-policy"
# (порожньо)
```

Не приходить **жодного**. Тож у таблиці нижче вони теж є.

### 1. HSTS — один перемикач

**Cloudflare → домен → SSL/TLS → Edge Certificates → HSTS → Enable.**

Каже браузеру ходити на сайт тільки через HTTPS, навіть коли людина
набрала адресу без нього. Закриває підміну з'єднання в чужому Wi-Fi.

⚠️ HSTS не можна швидко скасувати: браузери запам'ятовують його на
вказаний строк. Почніть із `max-age` на кілька годин, і коли
переконаєтесь, що все працює, підніміть до пів року.

Не вмикайте одразу `includeSubDomains`: під нього потрапить і
`dev.bestbrnd4u.com`.

### 2. Решта — одне Transform Rule

**Cloudflare → Rules → Transform Rules → Modify Response Header →
Create rule**, умова `All incoming requests`, і чотири рядки
`Set static`:

| Заголовок | Значення | Що дає |
|---|---|---|
| `X-Content-Type-Options` | `nosniff` | браузер не «вгадує» тип файлу |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | чужі сайти не бачать повну адресу, з якої прийшли |
| `X-Frame-Options` | `SAMEORIGIN` | сайт не вставлять у чужий iframe |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` | сторінка не попросить камеру чи мікрофон |

### 3. CSP — тільки в режимі звітів

Сувора політика на цьому сайті неможлива: у сторінках багато
вбудованих скриптів (штампи версій, `PRODUCT_DATA`, розбір
замовлення на сторінці подяки), а кожен із них вимагав би nonce —
тобто збірки під CSP.

Але **обмежити ДЖЕРЕЛА** можна й без цього: політика, яка дозволяє
вбудовані скрипти, але забороняє тягнути код із чужих доменів,
закриває головний реальний ризик — підмінений або доданий
сторонній скрипт.

Починати все одно з `Content-Security-Policy-Report-Only`: він
**нічого не блокує**, лише пише в консоль браузера, що заблокував
би. Кілька тижнів так — і видно, чи політика повна.

Той самий Transform Rule, ще один рядок:

**Header:** `Content-Security-Policy-Report-Only`

**Value** (одним рядком):

```
default-src 'self'; script-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net https://www.googletagmanager.com https://connect.facebook.net https://challenges.cloudflare.com https://static.cloudflareinsights.com; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data: https://img.youtube.com https://i.ytimg.com; connect-src 'self' https://*.supabase.co https://www.google-analytics.com https://region1.google-analytics.com https://www.facebook.com https://formsubmit.co; frame-src https://www.youtube-nocookie.com https://player.vimeo.com https://challenges.cloudflare.com; base-uri 'self'; form-action 'self' https://formsubmit.co; object-src 'none'
```

Перелік складено з ДІЮЧИХ джерел сайту, а не «про всяк випадок»:

| Джерело | Навіщо |
|---|---|
| `cdn.jsdelivr.net` | клієнт Supabase |
| `www.googletagmanager.com`, `*.google-analytics.com` | GA4 |
| `connect.facebook.net`, `www.facebook.com` | піксель Meta |
| `challenges.cloudflare.com` | Turnstile на оформленні |
| `static.cloudflareinsights.com` | лічильник Cloudflare (додає сам) |
| `fonts.googleapis.com`, `fonts.gstatic.com` | шрифт Inter |
| `*.supabase.co` | база й функція замовлень |
| `img.youtube.com`, `i.ytimg.com` | обкладинки відео товарів |
| `www.youtube-nocookie.com`, `player.vimeo.com` | самі відео |
| `formsubmit.co` | запасний шлях форми зв'язку |

⚠️ **Адмінку виключіть із правила** (`not starts_with(http.request.uri.path, "/admin")`):
Decap CMS вантажить свій код і звертається до GitHub, і під цю
політику він не потрапляє.

### Як перевірити

Моніторинг перевіряє заголовки сам і нагадує щодня, поки їх немає.
Руками:

```bash
curl -sI https://bestbrnd4u.com/ | grep -iE "strict-transport|x-frame|x-content-type|referrer-policy|permissions-policy|content-security"
```

А що заблокував би CSP — видно в консолі браузера на самому сайті:
рядки «would violate the following Content Security Policy directive».
