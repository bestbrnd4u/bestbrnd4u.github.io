# Кеш: два правила в Cloudflare

Це єдиний пункт у цьому проєкті, який робиться **не в коді**, а в
панелі. П'ять хвилин один раз.

## Що зараз не так

Заміряно на проді:

```
style.css, common.js, фото → Cache-Control: max-age=14400   (4 години)
HTML, catalog.json, sitemap → cf-cache-status: DYNAMIC       (край не кешує)
```

Два різні наслідки.

**Файли коду й фото несуть у адресі відбиток** — `style.css?v=c3a75572`.
Зміниться файл — зміниться відбиток, тобто адреса. Отже старий файл за
старою адресою **не може стати неправильним ніколи**, і тримати його
чотири години замість року — це просто зайві запити. Повторний
відвідувач через півдня качає ~1,5 МБ, яких у нього вже було.

**HTML і дані край не кешує взагалі.** `DYNAMIC` означає, що кожен
показ сторінки йде до GitHub Pages, хоч сторінка однакова для всіх.
Заміряно TTFB 90–110 мс; із кешу на краю було б 20–30.

GitHub Pages свої заголовки віддає такими, як вирішив сам, і змінити їх
із репозиторію не можна. А Cloudflare стоїть перед ним — і може
перевизначити.

---

## Правило 1: файли з відбитком — на рік

**Cloudflare → домен → Caching → Cache Rules → Create rule**

| Поле | Значення |
|---|---|
| Rule name | `Assets forever` |
| When incoming requests match | Custom filter expression |
| Expression | `(http.request.uri.path contains "/assets/") and (http.request.uri.query contains "v=")` |
| Cache eligibility | **Eligible for cache** |
| Edge TTL | Override origin → **1 year** |
| Browser TTL | Override origin → **1 year** |

Умова `v=` у запиті — навмисно: правило діє **лише** на адреси з
відбитком. Фото, додане через адмінку без відбитка, під нього не
потрапить і оновиться як звичайно.

⚠️ Саме тому важливо не прибирати відбитки з адрес. Їх ставить
`scripts/apply-cache-version.js` і `scripts/build-products.js`
(для фото).

## Правило 2: сторінки — на краю

| Поле | Значення |
|---|---|
| Rule name | `HTML at edge` |
| Expression | `(not http.request.uri.path contains ".") and (not starts_with(http.request.uri.path, "/admin")) and (http.host eq "bestbrnd4u.com")` |
| Cache eligibility | **Eligible for cache** |
| Edge TTL | Override origin → **2 hours** |
| Browser TTL | Respect origin (10 хвилин, як зараз) |

Дві години на краю, десять хвилин у браузері. Так змінена ціна доїжджає
до покупця за десять хвилин, а край при цьому знімає з GitHub Pages
майже все навантаження.

### Чому в виразі є домен

⚠️ Правила кешу діють **на всю зону**, а не лише на основний домен.
Без умови `http.host` правило сторінок затягувало під двогодинний кеш
ще й `dev.bestbrnd4u.com` — а чистка кешу стоїть тільки у продовій
виливці (`deploy-pages.yml`), тобто dev не чистить ніхто.

Заміряно:

```
dev.bestbrnd4u.com/catalog → cf-cache-status: HIT, Age: 120,
                             Cache-Control: max-age=7200
```

Виходило так: правку залито, збірка пройшла, Cloudflare Pages
опублікував — а на dev **до двох годин** та сама стара сторінка. І це
виглядає рівно як «зміни не поїхали», хоча вони на місці.

Тестове середовище кешувати на краю немає жодного сенсу: воно існує
саме для того, щоб дивитись свіже. `www` до цього не стосується — він
віддає 301 на основний домен і сторінок не показує.

### Чому вираз саме про точку в адресі

⚠️ У першій редакції цього документа стояв вираз
`http.request.uri.path contains "/"` — і він **збігається з усім**,
включно з `/data/catalog.json`. Тобто правило, написане для сторінок,
затягнуло під двогодинний кеш **залишки й ціни**: товар, який
закінчився, показувався б як наявний до двох годин. Заміряно на проді
після ввімкнення правила:

```
/data/catalog.json → Cache-Control: max-age=7200, cf-cache-status: MISS
```

Адреси сторінок цього магазину **не містять точки**: `/`, `/catalog`,
`/p/<slug>/`, `/brands/<slug>/`, `/order-status`. А все, що з точкою, —
це файли: `/data/*.json`, `/assets/*`, `/sitemap.xml`, `/feed.xml`,
`/robots.txt`. Перевірено: жоден slug товару, бренду чи категорії точки
не має (за цим стежить `tests/test-cache.js`).

Тому «немає точки в шляху» — це і є «це сторінка».

**Адмінку виключено окремо.** `/admin` — це Decap CMS: вона працює з
GitHub у реальному часі, і кешована сторінка там означала б, що
редактор бачить не те, що зберіг.

### Після другого правила обов'язково

**Caching → Configuration → Purge Everything** — один раз, щоб край
забув те, що встиг покласти до правил.

## Кеш і виливка: чому без очищення зміни не видно

Правило 2 має наслідок, який видно не одразу: **після виливки край ще
дві години віддає стару сторінку.**

Саме на це ми й натрапили. Sync branches відпрацював, прод-збірка
відпрацювала, у `main` усе на місці, файли на GitHub Pages нові — а на
сайті змін немає:

```
cf-cache-status: HIT
Age: 2883                    (48 хвилин у кеші)
Cache-Control: max-age=7200
```

В обхід кеша (`?cb=12345` — унікальна адреса) та сама сторінка
приходила вже новою. Тобто зламаного не було нічого: край просто не
знав, що сторінка змінилась.

### Тепер це робиться саме

`.github/workflows/deploy-pages.yml` після виливки викликає
`scripts/purge-cache.js` — і кеш спорожняється одразу. Крок стоїть
останнім і не може зробити деплой червоним: сторінка вже вилита.

**Що потрібно один раз:**

1. **Cloudflare → My Profile → API Tokens → Create Token → Custom token**

   | Поле | Значення |
   |---|---|
   | Permissions | Zone → **Cache Purge** → Purge |
   | Zone Resources | Include → Specific zone → `bestbrnd4u.com` |

   Більше прав не давайте: цей токен уміє рівно одне — чистити кеш.

2. **Zone ID** — на сторінці домену в Cloudflare, у правій колонці
   («API» → Zone ID).

3. **GitHub → Settings → Secrets and variables → Actions:**

   | Назва | Значення |
   |---|---|
   | `CLOUDFLARE_API_TOKEN` | токен із кроку 1 |
   | `CLOUDFLARE_ZONE_ID` | Zone ID із кроку 2 |

Поки секретів немає, крок пише попередження й завершується успішно —
сторінки оновляться самі за дві години.

### Якщо токен робити не хочеться

Поставте **Edge TTL = 5 minutes** замість двох годин. Тоді зміни
доїжджають самі за п'ять хвилин, а край усе одно знімає з origin
основну частину навантаження. Очищення тоді не потрібне взагалі.

---

## Чого НЕ треба робити

- **Не кешувати `/data/*.json` надовго.** Це залишки й ціни: десять
  хвилин, як зараз, — саме те, що треба. Товар, якого немає, показаний
  як «в наявності», коштує дорожче за зекономлені запити.
- **Не вмикати «Cache Everything» без виключень.** Під нього
  потрапить і адмінка, і `/data/`.
- **Не ставити Browser TTL на рік для HTML.** Тоді покупець із
  відкритою вкладкою не побачить нової ціни до кінця року.

## Як подивитись зміни на dev одразу після заливки

Між `git push` і видимою зміною на `dev.bestbrnd4u.com` стоять **три**
кроки, і кожен займає свій час:

| Крок | Хто робить | Скільки |
|---|---|---|
| 1. Перезбірка даних і сторінок | GitHub Actions → **Build dev environment** | 2–4 хв |
| 2. Публікація гілки | Cloudflare Pages (стежить за `dev`) | 1–2 хв |
| 3. Кеш на краю | Cloudflare | до 2 год *(поки в правилі немає домену)* |

⚠️ Крок 1 **сам робить другий коміт** у гілку (`chore(dev):
перезбірка`). Тому Cloudflare Pages публікує двічі: спершу ваш коміт,
потім перезібраний. Якщо дивитись між ними, видно напівзібраний стан —
нова розмітка зі старими `?v=` у скриптах.

### Перевірка за півхвилини

**1. Чи доїхала збірка.** Порівняти відбиток стилів на dev із тим, що
в гілці:

```bash
curl -s "https://dev.bestbrnd4u.com/catalog?x=$RANDOM" | grep -o 'style.css?v=[a-f0-9]*'
```

Той самий відбиток, що в `catalog.html` гілки, — збірка доїхала.
Інший — ще ні (або ви дивитесь із кеша, див. далі).

**2. Обійти кеш краю.** Будь-який випадковий параметр в адресі дає
інший ключ кеша, тож відповідь приходить із джерела:

```
https://dev.bestbrnd4u.com/catalog?x=12345
```

Це працює і в браузері — просто допишіть `?x=` і будь-яке число.
Оновлення сторінки через Ctrl+F5 тут **не допомагає**: кеш стоїть на
краю Cloudflare, а не у вашому браузері.

**3. Подивитись, що саме віддає край:**

```bash
curl -sSI https://dev.bestbrnd4u.com/catalog | grep -iE 'cf-cache-status|age:'
```

| Що бачите | Що це означає |
|---|---|
| `cf-cache-status: HIT`, `Age: 1500` | сторінка з кеша, їй 25 хвилин |
| `cf-cache-status: MISS` | свіжа з джерела |
| `cf-cache-status: EXPIRED` | кеш протух, край щойно взяв свіжу |

**4. Де дивитись самі кроки.** GitHub → **Actions** → останній запуск
*Build dev environment* (зелений — готово). Cloudflare → **Workers &
Pages** → проєкт dev → **Deployments**: там видно, який коміт
опублікований зараз.

### Щоб крок 3 зник назовсім

Додати в **Правило 2** умову домену (див. вираз вище):

```
and (http.host eq "bestbrnd4u.com")
```

Після цього dev завжди свіжий, а прод лишається під двогодинним кешем
із чисткою після виливки.

## Як перевірити

Моніторинг перевіряє це сам і нагадує щодня, поки не налаштовано:

```
✗ файли коду кешуються надовго (14400 с)
    → зараз 4 год — правило кешу в Cloudflare не налаштоване
✗ сторінки кешуються на краю Cloudflare
    → DYNAMIC — правило кешу для HTML не налаштоване
```

Після правил обидві стають зеленими. Руками:

```bash
curl -sI https://bestbrnd4u.com/assets/css/style.css?v=test | grep -i cache
```

Має бути `max-age=31536000`. І для сторінки:

```bash
curl -sI https://bestbrnd4u.com/ | grep -i cf-cache-status
```

Має бути `HIT` (або `MISS` на першому запиті — це «кешується, але ще
не в кеші»), а не `DYNAMIC`.
