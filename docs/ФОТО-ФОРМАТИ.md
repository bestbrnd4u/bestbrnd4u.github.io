# Фото: три ширини у двох форматах

Фото — **дві третини ваги** сторінки каталогу. Тому з них і знімається
найбільше.

## Що лежить на диску

Для кожного фото товару збірка робить копії:

| Файл | Ширина | Формат | Хто бере |
|---|---|---|---|
| `photo.webp` | 1200 | WebP | герой сторінки товару, зум |
| `photo-600.webp` / `photo-600.avif` | 600 | WebP + AVIF | картки каталогу на retina |
| `photo-300.webp` / `photo-300.avif` | 300 | WebP + AVIF | мініатюри, мобільна сітка |

Робить це `scripts/normalize-product-images.js` (крок `npm run
build:media`), і **лише для нових фото**: копія перезбирається, якщо її
немає або вона старша за базовий знімок.

## Чому AVIF

Заміряно на 24 справжніх файлах каталогу:

```
webp 399 КБ → avif 256 КБ     (на 36% менше)
```

На всіх 900 копіях: **10 МБ → 6 МБ**, тобто 63% від ваги WebP при тій
самій деталізації.

Якість `55` у AVIF відповідає `82` у WebP — формат стискає інакше, і
однакові числа означали б різну картинку.

### Чому 1200 лишився без AVIF

Широкий кадр — це герой сторінки товару, і він лежить у **статичній
розмітці**: браузер починає тягнути його на 238-й мілісекунді, ще до
будь-якого JavaScript. Підмінити формат потім означало б завантажити
фото **двічі** — гірше, ніж не підміняти взагалі.

Він важить 60 КБ і приїжджає раніше за LCP, тож там нема що
виправляти.

### Три файли, де AVIF трохи важчий

На майже білих мініатюрах (товар на білому тлі, 300 px) AVIF буває
важчим на 4–65 байтів: WebP там уже стиснутий майже до межі, а в AVIF
дає себе знати контейнер. Таких файлів **три з 900**, разом 107
байтів.

Тест це знає й дозволяє (`tests/test-avif.js`): поріг — кілобайт на
файл, а не «жодного байта». Інакше перевірку довелось би вимкнути
зовсім.

## Як обирається формат

Верстка **не має окремого переліку** для AVIF. AVIF робиться для
кожного фото, у якого є WebP-копії, тож «є в
`data/image-variants.json`» означає й «має AVIF».

⚠️ Саме тому важливо не реєструвати фото в переліку, поки обидва
формати не готові. За цим стежить сама збірка (`hasCopies` вимагає
обох) і тест.

Далі `applyImageVariants` в `assets/js/ui.js`:

1. один раз на сторінку перевіряє, чи браузер **розуміє** AVIF —
   декодуванням картинки 1×1, а не `canvas.toDataURL` (той показує
   вміння **записувати**, а це інша здатність: Safari довго вмів читати
   й не вмів писати);
2. підставляє в `srcset` адреси того формату, який браузер розуміє;
3. не розуміє — лишається WebP, як було.

### Чому не `<picture>`

`<picture>` із `<source type="image/avif">` — «правильний» спосіб, але
тут він означав би переписати розмітку карток, галереї, мініатюр і
статичного генератора — п'ять файлів і стільки ж тестів заради того
самого результату. Місце вибору формату вже існує: `srcset` картці
однаково проставляє JS.

### Чому це не вантажить фото двічі

Заміряно: `srcset` проставляється **раніше**, ніж браузер починає
тягнути `src` — картки ліниві, а JS відпрацьовує на ~500 мс. На проді
з 52 фото 48 приїхали зменшеними копіями й **жодного разу двічі**.

## Як перевірити

```bash
npm run build:media          # добудує копії для нових фото
node tests/test-avif.js      # усі формати на місці й легші
```

У браузері — консоль на сторінці каталогу:

```js
[...document.querySelectorAll('.product-card img')]
  .filter(i => i.currentSrc.includes('.avif')).length
```

Має бути майже стільки, скільки карток на екрані (кілька фото з
адмінки можуть бути без копій — вони лишаються WebP).

## Де це в коді

| Файл | За що відповідає |
|---|---|
| `scripts/normalize-product-images.js` | робить копії обох форматів |
| `data/image-variants.json` | перелік фото, для яких копії є |
| `assets/js/ui.js` | вибір формату й ширини (`buildSrcSet`, `avifSupported`) |
| `tests/test-avif.js` | формати на місці, легші, 1200 без AVIF |
| `tests/test-images-pagination.js` | ширини, пропорції, srcset для відомих фото |
