# Залишки товару

Скільки чого лишилось, хто це зменшує і що робити, коли товар
закінчився назовсім.

## Коротко

| Що | Де це вмикають |
|---|---|
| Скільки лишилось | Адмінка → товар → **📦 Залишки на складі** |
| Товар возять під замовлення завжди | Перемикач **📦 Товар під замовлення ЗАВЖДИ** |
| Товару більше не буде | Перемикач **🚫 Розпродано — прибрати з сайту** |

Залишки зменшуються **самі** після замовлення — див. «Списання» нижче.

---

## Як рахуються залишки

Рядок на колір, клітинка на розмір. У товару без розмірів (ONESIZE) —
одна клітинка на колір.

**Порожня клітинка — це не нуль, а «не рахуємо».** Товар із порожніми
залишками поводиться так, як до появи цієї можливості: продається без
жодних позначок.

Товар вважається закінченим, лише коли по **кожному** розміру кольору
стоїть явний **0**:

- нуль по всіх розмірах одного кольору → цей **колір** їде на сайт як
  «під замовлення»; решта кольорів продається як раніше;
- нуль по всіх кольорах → **увесь товар** стає «під замовлення»;
- окремий розмір із нулем → на сторінці товару він перекреслений, і
  вибір такого розміру перемикає сторінку в «під замовлення».

Чому саме так: якби порожнє означало нуль, достатньо було б заповнити
залишки одного кольору з трьох — і два інші мовчки зникли б з продажу.

---

## Списання після замовлення

Раз на десять хвилин workflow **Apply order stock** бере замовлення,
яких ще не врахував, і зменшує залишок того кольору й розміру, який
замовили. Потрібно швидше — Actions → Apply order stock → **Run
workflow**.

Скасоване замовлення повертає товар на полицю. Якщо скасування
скасувати (у панелі «Замовлення» таке можна), товар спишеться знову.

### Рахуємо з 5 вересня 2026-го

Крок дивиться лише на замовлення, зроблені **після появи залишків**.
Усе давніше в проставлених числах уже враховано: ви рахували те, що
лежить на полиці сьогодні, а не те, що колись було.

Це не теорія. Перший запуск взявся списувати всю історію магазину,
включно з тестами часів демо-каталогу, — і 12 товарів пішли в нуль за
продажі, яких сьогодні вже немає. Межа поставлена саме тому.

Якщо колись знадобиться інша точка відліку — змінна `STOCK_SINCE` у
кроці (значення за замовчуванням прописане в
`scripts/apply-order-stock.js`).

### Що потрібно увімкнути один раз

**0. Перенести в main.** GitHub бере розклад і кнопку «Run workflow» тільки з головної гілки. Поки workflow лежить лише в dev,
списання не запускається — ні за розкладом, ні вручну. Actions →
**Sync branches** → dev-to-main.

**1. Міграція.** Supabase → SQL Editor → виконати
`supabase/migrations/010-stock-applied.sql`. Вона додає в замовлення
прапорець «уже враховано в залишках» — без нього крок або списував би
одне й те саме щоразу, або втрачав замовлення.

**2. Один секрет GitHub.**

Settings → Secrets and variables → **Actions** → вкладка **Secrets** →
кнопка **New repository secret** (саме repository, не environment:
крок не оголошує середовища, тому секрети середовища до нього не
дійшли б).

| Поле | Що вписати |
|---|---|
| Name | `SUPABASE_SERVICE_ROLE_KEY` |
| Secret | ключ із Supabase → Project Settings → **API Keys** |

Який саме ключ: той, що дає повний доступ і обходить обмеження бази —
`service_role` у старому вигляді або `sb_secret_…` у новому. Не
`anon` і не `sb_publishable_…`: ними чужі замовлення не прочитати.

**Вкладка Variables не підходить**: її значення видно в логах кожного
запуску, а це ключ до всієї бази.

Адресу проєкту секретом задавати не треба — крок бере її з коду сайту
(`assets/js/supabase-client.js`), де вона й так відкрита.

⚠️ `service_role` обходить усі обмеження бази. Він має лежати
**тільки** в секретах (Supabase і GitHub) і ніколи — у коді сайту.

Поки секрету немає, крок нічого не робить і завершується успішно —
розклад не червонітиме.

### Чого це не робить

- **Не бронює товар у кошику.** Поки покупець думає, товар доступний
  іншим. Якщо двоє замовлять останню річ протягом десяти хвилин, ви
  побачите обидва замовлення й зателефонуєте — так само, як до появи
  залишків.
- **Не рахує повернення.** Прийняли товар назад — поверніть число
  руками (або скасуйте замовлення, тоді крок поверне сам).

### Якщо число здається неправильним

Найпростіше — виправити руками в адмінці: це джерело правди, і крок
списання не сперечається з тим, що ви вписали. Він лише додає й
віднімає за замовленнями, яких ще не бачив.

У логах workflow видно кожну зміну: `−1 файл · Колір / Розмір ·
замовлення 0708553442`. Там же — рядки «⚠», якщо щось не списалось:
товар видалили, колір перейменували, замовлення без кольору.

## Розпродано: замість видалення

Перемикач **🚫 Розпродано** прибирає товар із сайту цілком: з каталогу,
пошуку, добірок, карти сайту, бота. Замовити його не можна навіть під
замовлення — його просто немає.

Сам товар лишається в адмінці з усіма фото, описом, кадруванням і
артикулом. Зʼявиться знову — вимкніть перемикач, і товар повернеться
на **ту саму адресу**: id і slug за ним закріплені й нікому не
дістануться.

⚠️ Поки перемикач увімкнений, сторінка товару віддає 404. Старі
посилання (з реклами, з переписки) не працюють — це плата за те, що
товару немає ніде.

### Чим це відрізняється від «під замовлення»

| | Видно на сайті | Можна замовити |
|---|---|---|
| Залишок 0 | так | так, під замовлення |
| Під замовлення ЗАВЖДИ | так | так, під замовлення |
| Розпродано | **ні** | **ні** |

## Останній екземпляр не продається двічі

Списання в репозиторій іде раз на десять хвилин. Рівно стільки сайт
після продажу останньої сумки показував її як наявну — і двоє
покупців у цьому вікні отримували однакове підтвердження на один
товар.

Тепер перевірка живе **в самій базі**, у транзакції створення
замовлення. Друге замовлення на ту саму одиницю чекає на першому,
бачить його — і позначає свій рядок.

### Що ви побачите

У картці замовлення в Telegram (і в панелі замовлень) під товаром
зʼявиться рядок:

```
• Сумка Coach Tabby 26 (Coach)
   Темно-сірий / ONESIZE
   1 × 11 000 ₴
   ⚠️ залишку не було — під замовлення
```

Це означає: одиницю щойно забрало інше замовлення. Товар не
зникає й замовлення не скасовується — магазин і так торгує під
замовлення, тож ви просто домовляєтесь із покупцем про строк.

Відмовляти в замовленні автоматично не стали навмисно: це втрата
продажу там, де достатньо чесно сказати «цей поїде пізніше».

### Що треба зробити один раз

Виконати в **Supabase → SQL Editor** файл
`supabase/migrations/011-stock-reservation.sql` — вставити цілком і
натиснути Run. Плейсхолдерів там немає, повторний запуск безпечний.

Поки цього не зробили, все працює як раніше: захисту немає, а крок
«Оновити знімок залишків» у Actions світиться помаранчевим (він
навмисно не валить решту — інакше замовлення списались би двічі).

### Живий залишок на сторінках

Наявність на сайті бралась із зібраного каталогу — тобто з точністю
до десяти хвилин. Тепер сторінка товару, картки каталогу й кошик
питають базу: «що з цього ще є». Відповідь та сама, яку бачить
перевірка при створенні замовлення.

Питається один раз на завантаження сторінки, паралельно з каталогом
— тобто не сповільнює його. Якщо база не відповість за 1,2 секунди,
сайт покаже наявність зі збірки, як робив досі: живий залишок — це
уточнення, а не умова роботи магазину.

База віддає лише «так/ні», без кількостей: скільки саме одиниць на
полиці — відомості про оберти магазину, і сайт їх ніде не показує.

Для цього треба виконати ще один файл —
`supabase/migrations/012-live-stock.sql` (після 011).

### Живий залишок ПЕРЕКРИВАЄ каталог — і це головна пастка

Порядок такий: сайт малює наявність зі зібраного каталогу, а потім
**замінює** її відповіддю бази. Так і задумано — база знає
наявність у мить запиту, а файл відстає на десять хвилин.

Але це означає, що **знімок у базі мусить бути свіжішим за файл**.
Коли він застаріває, все перевертається: у каталозі правильні
числа, а на сайті — старі.

Саме це й сталось 7 вересня 2026-го. Виставили 100 штук трьом
сумкам Marc Jacobs, збірка dev перезібрала дані (у `catalog.json`
справді 100, `preOrder: false`), а на сайті всі три так і лишились
«під замовлення».

Причина: знімок кладе `scripts/push-stock.js`, і він запускався
лише в `build-products.yml` (прод) та в `apply-stock.yml`. У
`build-dev.yml` такого кроку **не було зовсім** — хоча адмінка на
dev комітить саме в dev. У базі лишався знімок часів «по одній
штуці», і живий залишок сумлінно перекривав ним свіжу сотню.

Найгірше в цьому — непомітність. Обидва джерела окремо виглядали
правильно: у каталозі 100, у базі «немає». Побачити можна було
тільки зіставивши їх.

**Виправлено:** крок знімка тепер є в обох збірках, а `npm test`
перевіряє, що він не зник ні з `build-products.yml`, ні з
`build-dev.yml`.

**Тепер про це повідомляє моніторинг.** `scripts/monitor.js`
зіставляє відповідь бази з каталогом і скаржиться, коли каталог
обіцяє 5+ одиниць, а база каже «немає». Менше п'яти не рахується:
одне-два розходження — це відкриті замовлення, тобто саме те, для
чого живий залишок і потрібен.

### База в dev і в проді одна

Адреса зашита в `assets/js/supabase-client.js`, окремого проєкту
для тестового середовища немає. Тому знімок залишків спільний:
**остання збірка будь-якої гілки задає наявність обом сайтам**.

Практично це означає одне: якщо ви на dev виставите нуль, щоб
подивитись, як виглядає «під замовлення», товар тієї ж хвилини
зникне з продажу і на проді. Зміни залишків краще робити тоді,
коли ви справді хочете їх застосувати.

### Якщо виставили залишок, а на сайті не змінилось

1. Перевірити, чи доїхали дані: відкрити
   `https://dev.bestbrnd4u.com/data/catalog.json` і знайти товар.
   Якщо там старе число — збірка ще не пройшла (Actions → **Build
   dev environment**).
2. Якщо в каталозі число нове, а на сайті старе — застряг знімок у
   базі. Actions → **Build dev environment** → **Run workflow**:
   останні два кроки й кладуть знімок.
3. Перевірити очима, що бачить браузер:

```bash
node scripts/monitor.js --env=development
```

Рядок «живий залишок не ховає товар, якого повно в каталозі»
назве конкретні товари й кольори.

### Чого це НЕ робить

Не рятує від одночасності в межах секунди: двоє, хто натиснув
«Купити» в ту саму мить, обидва побачать «в наявності» — сторінка вже
намальована. Але замовлення другого приїде з позначкою, і ви про це
дізнаєтесь одразу.

Не показує кількість. «Залишилась 1 штука» на картці могла б
підштовхнути до покупки, але це вже інше рішення — і про оберти
магазину воно розповідає більше, ніж варто.

## Де що лежить

| Файл | Що робить |
|---|---|
| `assets/js/stock.js` | правила: коли товар вважається закінченим. Один модуль на збірку, сайт і адмінку |
| `admin/stock-widget.js` | таблиця залишків у картці товару |
| `scripts/build-products.js` | розкладає залишки по кольорах і рахує «під замовлення»; прибирає розпродане з сайту |
| `scripts/apply-order-stock.js` | списання за замовленнями |
| `.github/workflows/apply-stock.yml` | розклад для нього |
| `supabase/migrations/010-stock-applied.sql` | прапорець «враховано» в замовленнях |
| `supabase/migrations/011-stock-reservation.sql` | перевірка залишку в мить замовлення |
| `scripts/push-stock.js` | знімок залишків у базу для цієї перевірки |
| `.github/workflows/build-dev.yml` | той самий знімок для гілки dev — без нього залишки з dev-адмінки не діють ніде |
| `scripts/monitor.js` | скаржиться, коли знімок у базі суперечить каталогу |
| `supabase/migrations/012-live-stock.sql` | функція, яка віддає наявність сайту |
| `assets/js/live-stock.js` | сайт питає базу й переносить відповідь у товари |
