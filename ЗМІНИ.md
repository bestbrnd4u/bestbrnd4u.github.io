# Що додано поверх вашого архіву

Розпакувати з перезаписом. Тут **лише те, чого у вашому архіві ще не
було** — правки з першої посилки (вісім пунктів + посилання в
замовленнях) у ньому вже є, я їх звірив рядок у рядок і не чіпав.

Сторінки з версіями ассетів (`?v=…`) не входять: їх перебудує
`npm run build`. `thanks.html` теж не входить — мої правки в ньому вже
застосовані, відрізнявся лише хеш вашої збірки.

## Після розпакування

```
npm run build
npm test
```

І **міграція**: `supabase/migrations/006-refusal-items-and-status.sql`
виконати в Supabase → SQL Editor, як 001–005. Вона зберігає перелік
позицій у заявці на відмову й переводить повністю відмовлене замовлення
у «Скасовано» — без неї кабінет покаже правильний статус, а список
замовлень магазину лишить «Нове».

## Що змінилось у зведенні кольорів через нові товари

Нові годинники й окуляри показали три діри — усі три полагоджені.

**«Сріблястий» розповзався між «Сірий» і «Білий».** Ключове слово було
«срібн», а в даних «Сріблястий» — спільного кореня немає, тож слово не
спрацьовувало й вирішував свотч. А свотчі в семи годинників різняться на
кілька відтінків: `#d9d9d9` потрапляв у білі, `#b7b4b4` — у сірі. Один
колір у двох пунктах фільтра — рівно те, від чого ми йшли. Тепер корінь
«сріб».

**Золотий годинник опинявся в «Жовтому».** `золот` було слабким словом
(в англійських назвах Coach і Michael Kors gold і brass майже завжди
означають фурнітуру, а не колір речі), тож вирішував свотч — а він у
золота жовтуватий. Тепер українське «золот» сильне, англійські
gold/brass лишились слабкими: коли магазин пише «Золотистий», він описує
саме річ.

**Половина назви губилась.** В окулярів Saint Laurent варіант записаний
як «Чорний / жовтий» — зведення брало найдовше слово й мовчки викидало
жовтий. У товару ставало два варіанти «Чорний», спрацьовував розвідник
зіткнень і робив із другого «Світло-чорний» — назву, якої не буває, для
оправи, що насправді чорно-жовта. Тепер складені назви зберігаються
цілком, а приставки «Світло-»/«Темно-» не чіпляються до чорного й
білого: далі світлішати нікуди.

Через це в `data/products.json` змінились три назви:

```
#72 варіант «Світло-чорний»  →  «Чорний / жовтий»
#79 «Сріблястий»             →  «Сріблястий / золотистий / чорний»
```

Фільтр: 11 сімей на 79 товарів (додався «Золотий»).

## Тести

`node tests/run-all.js` — 90 наборів, 2857 перевірок.

Два набори падали не через код, а через застарілі очікування — виправив:

- **test-catalog-order** перевіряв «найновіший товар перший у своїй
  категорії», не враховуючи, що сортування має два рівні: спершу
  наявні, потім під замовлення, і вже всередині групи новіші вище. Сім
  нових годинників — під замовлення, тож законно стали нижче за наявні.
  Впало очікування, а не сортування.
- Там же перевірка ручного порядку сама розставляла товарам номери
  10/20/30 — але в каталозі вже є три товари, закріплені з адмінки з
  номерами 1, 2, 3, і вони виявлялись першими. Тест падав на власній
  підготовці даних.

## Три речі в даних, які треба поправити вам

Тести знайшли їх на нових товарах. Це не код — це дані, тому лишаю як є.

**1. Немає фотографії.** Товар #74 «Годинник Tissot Lovely Round 19.5mm»
посилається на файл, якого немає в репозиторії:

```
assets/images/products/uploads/tissot-t-trend-lovely-mother-of-pearl-dial-ladies-watch-t0580091103100_4_1.webp
```

На картці й на сторінці товару там буде порожнє місце. Завантажте фото
або приберіть посилання. (Через це падають `test-media-filenames` і
частина `test-cache-busting`.)

**2. Артикули з пробілами.** У товару #72 «Сонцезахисні окуляри Saint
Laurent SL 276 MICA» артикули записані як `SL 276 MICA 001 53`, і в
першого варіанта sku немає взагалі. Перевірка вимагає артикул без
пробілів — його підставляють у фіди Merchant Center. (`test-merchant-listings`.)

**3. Залишок від старого механізму.** Файл `data/image-fingerprints.json`
лишився в репозиторії, хоча перейменування картинок за вмістом прибрано.
Видаліть його — архівом це зробити неможливо, zip уміє додавати файли,
але не видаляти. (`test-cache-busting`.)
